# Useful contextual returns under standing delegation

## Fresh general note/task message match

Before choosing an adaptive ticket, check whether this actual message contains new useful note/task content. Preserve that real content through the one ordinary intake batch; omit/defer an optional discretionary conversational return without consuming its rule. Do not silently drop intake, append another batch after opening a ticket, or invent another wire/turn/budget. A separately Owner-explicit date-specific trigger commitment is not discretionary: if it materially collides with new intake and no supported single bounded path fits, report the unperformed action honestly as pending and resolve the conflict from actual context; never erase it or claim content saved/trigger returned without its acknowledgement.

Fresh rule/source evidence requires an adaptive exception replacing ordinary intake for its actual authenticated Owner-message wake. A pre-submitted ordinary batch cannot construct reservation proof from its new match output. Submit `{"prepare_message_return":{"incoming_wire_id":"<actual-wire>","incoming_text":"<concise-actual-text>"}}` to installed `intake_tools.py --config <private-binding>`. It returns one bounded current match snapshot as `source` and an opaque host-created `ticket`. Review the selected exact saved evidence/purpose against actual context before returning it. Missing match, expired/stale rules, excessive scope or insufficient complete evidence hold or report no matching rule truthfully. The host records a conservative accounting reservation for the final acknowledgement before printing complete relevant candidate evidence. Source, control and complete output have no artificial local size ceilings; final actual output is also accounted without resetting the ticket.

Choose at most one COMPLETE returned match. Submit `continue_message_return` containing exactly the returned `ticket`, selected `rule_id`, its `expected_revision`, evidence `source_revision`/`source_digest`, and `match_confirmed:true`. These dependent proof fields come from the first output; no cached/fabricated digest is needed. The host uses its stored original incoming wire/text, verifies that selection/proof agrees with the stored snapshot and rechecks current rule/source/eligibility in the reservation transaction. Correction, exclusion, task completion, consumed allowance or stale revision between stages holds before another slot is consumed. Success returns `source.status:"response_slot_reserved"`, finite remaining count and delivery unconfirmed; then use the normal actual-message reply once. It creates no timer or alternate sender.

Both steps share persistent source/control/complete counters, at most two source emissions and a fifteen-minute review window (assistant-default work limit). The final source acknowledgement is conservatively charged at preparation and never refunded/reset. Restart or duplicate prepare for the same original wire returns its existing ticket/state with `new_budget:false`, charges control and cannot renew proof/budget. Changed incoming text cannot rebind it. A completed/failed ticket cannot grant a new slot; retry/uncertainty never authorizes resend. Permanently stopped tickets emit no further model output. Missing, stale or unverifiable evidence is a hold, not a reason to page, poll or create a new turn identity.

Generic and saved legacy task-trigger ticket modes are mutually exclusive for one actual incoming wire; choose the relevant workflow from real context. Preparing the other mode is charged/refused under the existing ticket and cannot mint a second budget. Do not add an ordinary intake batch to either workflow. Tickets/wire strings/booleans are bookkeeping/provenance, not an independent authenticator: the trusted assistant verifies the actual Owner envelope and semantic relevance, never a peer/quoted/fabricated trigger. These accounting counters do not measure complete model/session billing. Finite workflow call permissions remain; they do not cap the size of complete relevant evidence.

## Intake decisions and finishing

For every authenticated Owner message, apply the entrypoint's fact-based presumption in favor of a useful proactive follow-up, even if the Owner did not say “remind me.” Choose `no_return` only with an adequate objective reason grounded in actual message/source evidence. Examples include explicitly confirmed completion with no remaining relevant step, an explicit opt-out covering this purpose, an existing mechanism covering the same episode, an exhausted finite allowance, or content explicitly presented only as a hypothetical example. Do not infer completion, disinterest or uselessness. A saved idea alone never becomes a timer: evaluate the real purpose and commit the selected supported mechanism. Under verified standing Owner delegation, choose an appropriate opportunity from real context and the confirmed private timezone without routine renewed permission/time questions. Materially missing context or failed materialization remains an honestly reported unresolved/partial commitment, not a successful schedule or a speculative `no_return` justification.

The reviewed private operator policy records its version and authenticated delegation pointers. Its conservative numeric values are **assistant-selected defaults**, not Owner-specified preferences: one initial return per unresolved purpose, zero automatic children, maximum seven-day relevance from the episode's original intake clipped to an earlier real deadline, default one-hour late window clipped to relevance, and3600-second spacing where a repeat applies. These are upper limits, not an instruction to wait seven days. Choose timing within a real stated opportunity/date/window. Without a known actionable timed horizon, consider one next-relevant authenticated-owner-message trigger with finite expiry; this is pending new input, not a timed wake or guaranteed delivery. Explicit owner-requested repeated timers use the existing finite count/deadline/spacing contract; standing discretion never replenishes them.

`return_plan` stores the intake decision separately from source revisions:

- Exact `ref` (`note:<id>`/`task:<id>`), `expected_source_revision`, decision CAS `expected_revision` (zero new).
- `decision`: `no_return`, `unresolved_context`, `planned_timed`, `planned_message`.
- Concise `reason`, stable specific `purpose` describing the real episode, `authority_ref` matching the operator-verified standing delegation for planned returns.
- Planned mechanisms add finite UTC `deadline` and stable `mechanism_id` (timed operation ID or message rule ID).

A purpose/source episode is durable across revisions/repeated mentions/restarts. Do not paraphrase its purpose or choose another source ID/rule ID to obtain another budget. The episode has one selected mechanism; timed and message returns cannot independently represent the same discretionary purpose. Source-bound new note timers require its exact planned operation; existing task timers continue their normal workflow. A genuine separately Owner-explicit single contextual task create colliding with an existing decision carries `owner_request_wire_id` in its durable operation receipt. This must refer to the actual authenticated instruction, verified by the trusted assistant; an arbitrary string/source text does not grant permission. Existing explicit fixed/finite repeat workflows remain available. Planned state has `return_committed:false`; source save/planning is not a scheduled wake. After ANY rule materialization or source journal preparation/mapping, the original plan identity is frozen, even before commit ACK and after rule cancellation/consumption. Reconcile the same identity; never switch mechanisms through a crash gap. Existing committed episodes cannot be reset. Correct a still-useful existing timer via its exact reminder/journal CAS, retaining count/deadline/purpose. Completion/cancellation/exclusion makes it unsendable, without replenishing its allowance.

## Finish in the actual intake wake

Use ONE stdin object with `calls` (one to three bounded source calls) and `finish_return`, with no preferences/recall branch. `finish_return` contains `kind` (`message`/`timed`), exact `ref`, `expected_source_revision`, planned decision `expected_revision`, plus `rule` or `timer`. Usually `calls` save source and `return_plan`; optional third call indexes the current summary. The deterministic finish creates one mechanism and commits its acknowledgement, printing one complete combined result without artificial local source/control/complete-output size caps. It is not four model recovery calls or a second intake batch.

For `message`, `rule` is the exact `note_rule_put` argument object documented below. The source calls, rule and acknowledgement commit atomically; schema, revision, relevance or call-permission failure rolls them all back. Relevant evidence is not rejected or truncated for its size. For `timed`, `timer` is the exact configured `reminder_tools create` argument object, including immutable `operation_id` and `expected_source_revision`; the finisher executes the existing journal and then verifies/commits `return_commit`. Relevance/late window are checked before source preparation. No sender is called.

A timed source/journal/ledger finish cannot be a single SQLite transaction. Before source commit the combined envelope records a conservative control accounting reservation; after it, a failure returns `status:partial` plus `source_committed:true`, `return_committed:false`, `held_reconciliation_required`, immutable `mechanism_id`. Never claim a promised/scheduled return without its exact receipt. A process crash can produce no ACK while stores changed. The deterministic recovery route is the SAME installed finisher with one `return_get` call and the identical `finish_return` request (current decision revision); it resumes only that journal/rule identity and acknowledges its receipt, without changing due time or creating another timer. This recovery is authorized reconciliation of the known interrupted mutation, not ordinary automatic recall/retry or waiting for hypothetical future input. If source/plan/request no longer match, hold for explicit private reconciliation. Already committed recovery remains historical scheduling evidence, not current delivery proof.

For a timed plan, create through the configured `reminder_tools.py create` with exact `operation_id`, `expected_source_revision`, contextual source ref, selected local date/time/confirmed IANA zone, `followup_limit:0`, and clipped finite late window. Preserve the operation ID after a crash; the journal resumes its exact receipt, never invent a timer. Then `return_commit` takes exact ref/decision revision/source revision and actual `reminder_id`. It verifies the current source mapping plus the configured external journal's complete stage and linked ledger receipt with no due hold, current contextual reminder, finite deadline/late window and zero further chain. An incomplete/uncertain/expired/mismatched operation holds. Commit confirms scheduling, never queue admission/send/receipt.

For a message plan, `note_rule_put` stores `id`, `expected_revision:0`, and a complete `record`: `note_id`, `note_revision` OR `task_id`, `task_revision` (never both), the exact plan `purpose`, one to four normalized literal `match_terms`, `count:1`, finite `until_utc`, `min_seconds:3600`, `permission_kind:"delegated"`, `permission_source` matching standing authority and its `permission_wire_id`. The rule ID/purpose/source/revision/count/spacing/deadline must match the plan. No manufactured note is needed for a task. Explicit separate owner-requested finite message rules use `permission_kind:"owner_explicit"` and exact real permission provenance/count; they do not reset an existing purpose. Duplicate purpose rules are refused. Commit uses `return_commit` with ref/decision revision/source revision; no reminder ID. It verifies a current unexpired finite rule, then reports pending matching input, not scheduled timed delivery. Existing symbolic/date-specific task commitments use the dedicated [targeted adapter](task-triggers.md), preserving explicit trigger-relative repeats rather than converting to a new discretionary episode.

On an actual matching authenticated Owner-message wake with already verified current rule/source proof, use `note_match` with that exact `incoming_wire_id` and complete relevant `incoming_text` describing the actual match, without a local byte or word cutoff. No idle poll, fabricated trigger, scheduler wake or peer message qualifies. It checks current source/rule revision, active state, finite count/expiry/spacing and exact wire dedup under bounded candidate/output work. It returns complete matching purposes/curated sources within the exact authenticated message scope; choose at most one useful conversational return in the normal reply. Use `note_rule_use` with rule `id`, `expected_revision`, same actual wire/text, `note_revision` and current `note_digest` before composing/sending that return. The durable CAS reservation consumes allowance and stores provenance; it never sends. A retry returns `already_reserved` with no repeat allowed. A crash/uncertain reply burns that reserved slot, rather than risk duplicate delivery; do not claim confirmed send/receipt from a reservation. Normal direct-reply routing applies once, with no extra scheduled sender. Future genuine matching messages can only use an unconsumed still-relevant rule.

Task results from `note_match` contain `task` rather than `note`; reservation `note_rule_use` then takes exact `task_revision`/`task_digest` instead of note fields. Source kind/ref/revision/digest/current eligibility must agree. The generic historical table names do not imply tasks became notes.

Correction immediately disables old message-rule eligibility without resetting count/deadline. `note_rule_rebind` can explicitly continue an unconsumed **same-purpose correction** using rule ID/revision, current `note_revision` OR `task_revision` and concise `rationale`; it keeps the original allowance/expiry/spacing. Consumed, cancelled, forgotten, archived, resolved or completed rules cannot rebind/resurrect, including inactive correction continuations that were later excluded/closed. Task reopen/restore cannot undo this terminal invalidation. `note_rule_cancel` uses ID/revision and preserves its exhausted history. Existing genuine task/message intents in earlier private source partitions remain authoritative; do not bulk-import or replace them with fixtures/new rules.

`return_get` takes an exact ref and exposes stored decision/receipt **as historical commit evidence**; current delivery/mechanism state is not inferred from the stored receipt. Inspect the exact current runtime reminder/rule if needed within its applicable budget. It reports current source relevance/revision separately and hides all derived purpose/reason/receipt after note forget/archive. A terminal/currently irrelevant intent never grants another return. Due contextual work uses the existing [event-bound wrapper](contextual.md), relevance/claim/dedup guards and approved Telegram route; no alternate sender, timer duplication or periodic model polling.
